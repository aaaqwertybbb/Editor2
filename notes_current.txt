<
Your virtualized scroll logic is incredibly well-optimized. You are already utilizing high-performance patterns: avoiding innerHTML layout thrashing by using CharacterData.replaceData(),
leaning on a ring buffer to mutate a bounded pool of DOM nodes, and offloading structural translation shifts to the GPU via 32-bit integer-driven translate3d/translateY.

However, executing this directly within a critical RequestAnimationFrame (rAF) block while scrolling exposes a few clear, high-impact bottlenecks. The primary bottleneck in this pipeline
is layout/paint thrashing caused by mixing style invalidations (.style.transform = ...) and immediate DOM text node mutations inside the loop, paired with synchronous syntax highlighting.

The key performance issues and their structural solutions are outlined below.

Critical Bottlenecks & Optimizations

1. Decouple DOM/Style Mutations to Prevent Layout Thrashing
- The Problem: Inside your for loop, you change text contents (replaceData) and immediately modify styles (div.style.transform = ...).
               Even though transform doesn't trigger layout cascades, modifying raw text nodes forces layout and layer tree invalidations. Alternating between text manipulation and
               style writes across consecutive DOM elements inside a loop causes the browser to constantly schedule and merge style recalculations during a single frame execution.
- The Fix: Split your loop into two rapid sequential passes, or batched operations.
           First, update all raw data/text states (replaceData). Second, perform a clean sweep to update all layout/transform offsets (translateY).

2. Evict Immediate Syntax Highlighting from the rAF Thread
- The Problem: When permitImmediateSyntaxHighlighting is true, you call EDI_syntaxHighlight_parallelArray(div, ...) synchronously inside the scrolling loop.
                 The CSS Custom Highlight API is incredibly fast because it decouples highlighting from the DOM structure, but evaluating the text ranges,
                 querying token boundaries, and modifying highlight collections during an active scroll event will inevitably drop frames.
- The Fix: Remove immediate syntax highlighting entirely while scrolling. Trust your setTimeout trailing-edge logic (or use an IntersectionObserver / requestIdleCallback)
           to token-highlight only when scrolling slows down or halts. If you must have immediate highlights, offload the text processing to a Web Worker, and
           only apply the CSS Highlight range updates on the main thread via a batched queue. Your inline note is correct: Eating the cost of a full viewport highlight on
           the trailing edge is significantly faster than tracking micro-flags and executing synchronous checks per line during layout updates.

3. Eliminate translateY String Allocations
- The Problem: const translateY = 'translateY(' + vertical + 'px)'; allocates a new string object on every single line iteration. For a fast scroll spanning hundreds of lines,
               this triggers micro-garbage collection (GC) pauses inside your tight rAF loop.
- The Fix: Instead of translating each individual line container separately, place your visible line div elements into a relative or absolute coordinate block where their relative
             offsets are fixed, or maintain their translations statically. Alternatively, if they must shift dynamically, cache the string values or
             move the parent canvas container rather than iterating transforms on every single child node.

4. Array Layout and INTS Array Dereferencing Overhead
- The Problem: JavaScript engines optimize typed arrays or packed arrays well, but nested lookups like INTS[fEDI_lastReadNumber_scrollTop] add
               pointer overhead inside hot calculation loops when repeated excessively.
- The Fix: Localize constants before the loop. You did this nicely with several variables, but ensure that any state modified
           inside the loops uses plain local JavaScript primitives (let or const integers) rather than resolving an index against the global INTS array.

Structural Comparison


Strategy         | Current Implementation                                      | Optimized Target Architecture
----------------------------------------------------------------------------------------------------------------------------
DOM Execution    | Interleaved replaceData and style shifts per line.          | Batched replaceData pass -> Batched CSS transform pass.
Highlighting     | Synchronous highlight application during active scrolling.  | 100% Deferred to Trailing-Edge debounced microtask.
Memory footprint | Continuous string allocations (translateY) per node update. | Static layout pool or cached translation indices.

<
No, "AST Facade" is not the most accurate name for this specific feature.
While it conveys the idea of a simplified or high-level view, it doesn't capture the dynamic, position-dependent nature of what you are building.

In the context of editor clients and Language Server Protocol (LSP) architectures, the pattern you are describing—where a structural path or contextual subset of the syntax tree is
extracted based on the cursor's location—is widely recognized.

Why "Facade" Falls Short

In software engineering, a Facade hides a complex subsystem behind a single, static interface. Your feature is highly dynamic, context-aware,
and bound to a changing coordinate (the cursor).

More Accurate Architectural Names

Depending on how this data is structured and used, here are the industry-standard terms for your feature, ranked from most accurate to least:

1. Cursor Context / Node Path
- What it means: The exact ancestral chain of AST nodes from the root down to the specific token under the cursor.
- Why it fits: Editors frequently use this to display the current "breadcrumbs" at the top of the window (e.g., Class -> Method -> IfStatement).

2. Focused AST / Structural Viewport
- What it means: A scoped-down projection of the full AST that only includes nodes relevant to the user's current edit focus.
- Why it fits: It emphasizes that you are filtering the massive full tree into a manageable, local "window" centered on the cursor.

3. Zipped AST (or Zipper Pattern)
- What it means: A functional programming pattern used to represent a data structure along with a pointer to a specific location inside it, allowing for efficient local updates.
- Why it fits: If your "partial replica" maintains a way to walk back up to the root or modify the tree locally at the cursor, it is structurally a Zipper.
