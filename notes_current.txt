< However, looking at the layout of your JS_line_lex loop, there are a few massive architectural and performance bottlenecks lurking here.
< 
< 1. The Global Range Bottleneck (Critical)
< 
< Because you instantiate your Highlight objects globally at the top, if you run this lexer on every line,
< you are likely appending new Range objects to the same global highlights continuously.
< - The Issue: If you don't clear the ranges for the specific lines being re-lexed or out of view, the Highlight sets will grow indefinitely.
<   The browser will eventually choke trying to track hundreds of thousands of overlapping ranges.
< - The Fix: You need a system to cleanly remove a line's old ranges before calculating its new ones.
<   Usually, editors map a line's ID to its active Range objects so they can be .delete()d from the global Highlight set when the line changes or leaves the viewport.
< 
< 2. High-Performance Garbage Collection Rules
< 
< Inside a fast, synchronous scrolling loop, allocating objects inside the while loop is the #1 cause of frame drops (jank).
< When the browser garbage collects hundreds of temporary objects, the UI freezes.
< - let range = new Range(); should never be instantiated inside the line loop if you can avoid it, and absolutely never inside the while loop.
< - The Trick: Instantiation of a Range is relatively expensive. Instead, instantiate a pool of Range objects, or only create them exactly when a token match is finalized.
